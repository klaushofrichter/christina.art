# CLAUDE.md

Operational context for working in this repo.

## What this is

The website of the artist **Christina Schwarz**, served at
`christinaschwarz.art`: an Express/TypeScript app deployed as a Knative
Service on the `kube-setup`-managed k3s cluster. It is modelled on
`klaushofrichter/art` (same layout, workflows and release process); when in
doubt about a pattern, that repo and kube-setup's
`docs/cluster-deployment-requirements.md` / `docs/repository-baseline.md` are
the references.

One page, in this order: her name, the **works** (one at a time, large,
each opening into a lightbox), **exhibitions** (upcoming, then past) and
**about** (portrait, short bio, contact). The mood is Klaus's brief of
2026-11-08: *muted, understated, subtle highlights, a slow and steady
atmosphere*, and **it must work very well on a phone**. The site is
experimental and will be iterated on.

**All visitor-facing text is in three JSON files, compiled at build time.**

| File | Holds |
|---|---|
| `content/bio.json` | `artist`, `tagline`, `description`, `email`, `bio` (paragraphs) |
| `content/works.json` | `works`: `image` (the picture's slug), `title`, `year`, `medium`, `size?`, in page order |
| `content/exhibitions.json` | `exhibitions`: `title`, `kind`, `venue`, `city`, `from`, `to` (YYYY-MM-DD) |
| `content/images.json` | generated by `npm run images`; never edit by hand |

`npm run build` runs `scripts/build-content.ts`, which checks all four
(`loadSite` in `src/content.ts`) and writes `dist/content.json`; the server
reads only that. So the files are read **at build time, in the deploy's
Docker build**, never at runtime, and they can be fed from elsewhere ahead of
a deploy (Klaus, 2026-11-08). Bad data fails the build, naming the file,
before anything rolls out.

**The content can be edited in the Google Sheet "content"**
(https://docs.google.com/spreadsheets/d/1hdMzpoa5A8JrmHo70GWsRPYjOqpItfwZVrvAmQOGS_c/,
owned by klaus.hofrichter@gmail.com, klaus@klaushofrichter.net is an editor):
tabs `meta` (each file's `_note` and `placeholder`), `bio` (key | value, one
`bio` row per paragraph), `works` and `exhibitions` (one row per entry; the
layout is documented in `scripts/sheet-format.ts`). The `Info` tab is Klaus's.
`npm run sheet` reads it and writes the three files **byte for byte** in the
repository's format, after checking the result with the build's own loader;
`npm run sheet -- --check` only reports differences. It is run by hand before
a deploy, never automatically. `npm run sheet:csv` goes the other way (JSON to
one CSV per tab). The round trip is tested in `test/sheet.test.ts`.

Access: the script reads through the Sheets API with an OAuth
`authorized_user` credential from `GWS_CREDENTIALS_JSON` (or the file in
`GOOGLE_WORKSPACE_CLI_CREDENTIALS_FILE`), the same credential the
`@googleworkspace/cli` (`gws`) uses; cloud sessions have it as an environment
variable. To use `gws` itself, write the variable to a 0600 file and point
`GOOGLE_WORKSPACE_CLI_CREDENTIALS_FILE` at it. Never print the credential. In
a cloud sandbox, Node needs `NODE_USE_ENV_PROXY=1` and
`NODE_EXTRA_CA_CERTS=/root/.ccr/ca-bundle.crt`; `docs.google.com` (the CSV
export) is blocked there, `sheets.googleapis.com` is not.

**The DEMO sash** (cams.skylar.technology's amber corner sash) shows while
any of the three files has `"placeholder": true`. The bio, titles, years and
exhibitions in them now are **placeholders Klaus asked to be made up**
(2026-11-08); don't present them as fact anywhere else. When real data
arrives, drop the flag and the sash goes with it. The email address is real.

**The footer shows the release** as `v<YYYY.MM.DD.N>` (`dev` locally), from
`APP_VERSION`. The deploy smoke test greps the live page for
`<span class="ver">v<version></span>` and quotes it in the release notes.

Fully public: no OAuth, no sessions, no secrets, no `.env`. The only
configuration it reads is `PORT` (and `APP_VERSION`, stamped by the deploy).

## Pictures: `npm run images`, and never any metadata

1. New works go into `images-incoming/`, a new portrait to `assets/c1.png`.
   Both folders are git-ignored: they are inputs, never committed.
2. `npm run images` (`scripts/images.ts`) turns each into a **master** in
   `originals/` (upright, sRGB, ≤3200px, JPEG) and removes the incoming
   file, then writes **derivatives** to `public/img`: AVIF, WebP and JPEG at
   several widths, named `<slug>-<width>.<hash>.<ext>`. It also writes
   `content/images.json` (sizes, widths, hash, a muted loading colour) and
   the favicon set from `public/favicon.svg`.
3. Add the work to `content/works.json` (its `image` is the file's slug).
4. Commit `originals/`, `public/img`, `content/`.

**The repo is public and phone photos carry GPS coordinates, the camera and
the time.** The pipeline writes no EXIF/XMP/IPTC, and
`test/content.test.ts` fails if any picture under `originals/` or
`public/img` carries any. Never commit a camera original; never call
sharp's `withMetadata()`/`keepExif()`. The first six were stripped with
exiftool on the node before they were pushed (branch `images-incoming`),
and the unstripped originals exist only there.

Derivative names carry a content hash, so `/img` is served
`immutable` for a year. `site.css`/`site.js` are linked with `?v=<hash>`.
`originals/` is excluded from the Docker image; `content/` is in it.

## The page, the script and the CSP

Server-rendered (`src/views/page.ts`), escaped, no framework. One script,
`public/site.js`, loaded in `<head>` without `defer` so the `js` class lands
before first paint; it does the slow reveals, the fade-in over each
picture's muted colour, and the lightbox (keyboard, swipe, and Back closes
it). Without JS the page is complete and every work links to its largest
JPEG. The CSP allows only same-origin styles, scripts and images: **no
inline `<script>` or `style=""`** (colours are set through the CSSOM). The
deploy smoke test greps for `<h1>Christina Schwarz</h1>`, so keep that
heading exactly.

## Names

- Repo and image: `christina.art`, `ghcr.io/klaushofrichter/christina.art`.
- Kubernetes names cannot contain dots, so inside the cluster everything is
  **`christina-art`**: the namespace, the ksvc, labels. The runner lives in
  **`christina-art-runner`**. The manifest is
  `kube-setup/manifests/christina-art/christina-art-ksvc.yaml`.
- `christinaschwarz.art` is canonical. `www.christinaschwarz.art` must 301 to
  it with path and query kept.

## The www redirect

A Knative `DomainMapping` can rewrite the Host header to the ksvc's internal
name before the request reaches the pod, so an in-app redirect keyed on the
host may never see `www.`. kube-setup already has a proven cluster-side
pattern for exactly this (`manifests/insta/insta-legacy-redirect.yaml`: a
Traefik `redirectRegex` IngressRoute in `kourier-system`, priority 1000, ACME
path exempted, with the www certificate kept on the knative-gateway Ingress).
That is the recommended primary. `src/canonical.ts` redirects too, reading
`req.hostname` (Host, or X-Forwarded-Host through `trust proxy`), and is the
fallback if the original host does reach the app. The deploy's smoke test
checks the behaviour from outside either way, accepting 301 or 308 (Traefik
answers HEAD/POST with 308).

## Branches

- `main`: development, unprotected. A push builds and pushes `:main`, that
  tag and no other (`build-push.yml`). Not deployed.
- `production`: protected, PR-only from `main`. A merge runs
  `deploy-production.yml` on the in-cluster self-hosted runner
  (`[self-hosted, k3s]`, registered to this repo only).

**Only the deploy writes a production tag** (`:<sha>`, `:v<version>`,
`:latest`). The manifest pins `:<sha>`; a main build writing the same tag
would replace the released image under the pin.

Required checks on `production`: `test`, `codeql`, `e2e` (each is its own job
in `production-checks.yml`, so each reports its own context).

**Never merge into `production` on your own.** Releases happen with Klaus's
approval.

## Versioning and releases

`vYYYY.MM.DD.N`, generated in the deploy from the existing release tags,
dated `TZ=America/Chicago`. `package.json` carries no version. The value
reaches the image as `ARG APP_VERSION` and `/health` reports it; the smoke
test polls until the live `/health` reports the version that run stamped.

Notes: `## [Unreleased]` in `CHANGELOG.md`, then the commits since the last
release, then "Verified at release" from the smoke test
(`scripts/release-notes.sh`, renderable locally with stub values; see its
header). **Empty `[Unreleased]` as part of promoting**:
`scripts/check-changelog.sh` fails `test` on a PR into `production` that
would republish the previous notes.

## Node 26, in three places that move together

Both `Dockerfile` stages (`node:26-alpine`), `node-version:` in every
workflow, and `@types/node` in `package.json`. Take a Node major bump from
Dependabot in all three or none.

## Container

`USER 1000:1000` (numeric, so the image is non-root on its own). The `test`
check builds the image and runs it with no `--user` to prove it. The ksvc in
kube-setup carries the matching non-root, drop-ALL `securityContext` with
`runAsUser`/`runAsGroup: 1000`.

## Don't run Playwright on the self-hosted runner

It is capped at 512Mi and a browser install OOM-kills it (GitHub reports it
as "lost communication with the server"). Playwright runs in the `e2e` job on
GitHub's runners; the deploy smoke-tests with `curl` and `sed` (no `jq` there).

Locally, if Playwright's own browser is not installed, point it at one with
`PW_CHROMIUM_PATH=/path/to/chrome npm run test:e2e`.

## Cluster side

Lives in `klaushofrichter/kube-setup` and is changed by the kube-setup
session, not from here: `manifests/christina-art/` (ksvc, DomainMapping) and
`manifests/christina-art-runner/` (runner namespace, ServiceAccount, RBAC,
NetworkPolicy). Secrets: `KUBE_SETUP_DEPLOY_TOKEN` (Actions secret in this
repo) and `runner-pat` (Kubernetes Secret in `christina-art-runner`).
